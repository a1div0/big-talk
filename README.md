# big-talk

Spec-driven design политической системы. Репозиторий, в котором конструкция политической
системы разрабатывается так же, как программная: спецификация, решения с обоснованием,
тесты, CI, агенты. Цель — описание устойчивой непротиворечивой системы, достаточно
проверенное, чтобы запустить пилот на субнациональном уровне.

## Быстрый старт

```bash
git clone git@github.com:a1div0/big-talk.git && cd big-talk
pip install -r tools/requirements.txt
make lint      # инварианты графа
make matrix    # какие требования чем покрыты
make budget    # потребление бюджета сложности
```

Порядок чтения для нового участника: `CONSTITUTION.md` → `axioms/` → `requirements/` →
`tests/README.md` → `spec/EL-001` → `adr/ADR-0001` → `tests/runs/RUN-0001`. После этого понятно,
как выглядит один полный цикл.

## Как внести изменение

Аналог `specify → plan → tasks` из SDD:

1. **Заявка.** Issue или OQ в `registry/`: что не так, какой REQ нарушен или какой DEF найден.
2. **ADR.** `python tools/new.py adr <slug>` (или скилл `write-adr`). Минимум две альтернативы,
   стилмен отвергнутой, ссылки на ≥2 прецедента, принятые риски как отдельные RISK.
   Если прецедентов нет — сначала `add-precedent`.
3. **Пре-ревью агентами.** `red-team` → новые THR; `stakeholder-roleplay` → новые DIS;
   `lint-and-trace` → бюджет и покрытие. Всё в статусе proposed/open.
4. **Правка EL.** Формулировка из «Решения» ADR — в «Правила» EL. Обновить `decided_by`.
5. **Тесты.** `run-thought-test` для TEST-001, 002, 004, 011 минимум; для процедур
   назначения/голосования — плюс 006, 009, 010. Каждый низкий балл → DEF/OQ.
6. **Нормативный текст.** `draft-normative` → NORM с таблицей соответствия.
7. **CI.** `make lint` зелёный.
8. **Ревью людьми** по ролям из `CONSTITUTION.md` §2: конструктор не принимает своё,
   красная команда и историк — обязательны для accepted.
9. **Merge.** Переводить в accepted может только мейнтейнер и только по Definition of Done
   (`CONSTITUTION.md` §5) — линтер проверяет формальную часть автоматически.

## Как прогнать тест

Вручную: открыть `tests/TEST-NNN`, пройти «Процедуру», заполнить рубрику, создать
`tests/runs/RUN-NNNN-<TEST>-<EL>.md` из шаблона, для каждого балла 0/1 — DEF или OQ.

Агентом: скилл `run-thought-test`. Ограничение: агент не тестирует EL, который сам писал в той
же сессии. Это записано в `CONSTITUTION.md` §2 и в самом скилле.

Когда какие тесты — `tests/README.md`.

## Как использовать агентов

Скиллы лежат в `skills/`, формат — `SKILL.md` с frontmatter `name`/`description`. Агент читает `CONSTITUTION.md` и нужный скилл,
создаёт артефакты через `tools/new.py`, гоняет `tools/lint.py`, открывает PR.

| скилл | когда |
|---|---|
| `write-adr` | любое изменение `spec/` |
| `add-precedent` | ADR ссылается на историю без PREC |
| `run-thought-test` | проверка EL по каталогу тестов |
| `operational-walkthrough` | прогон процедуры по ролям — ближайший аналог запуска кода |
| `stakeholder-roleplay` | у EL/ADR нет ни одной DIS — значит, разногласия не искали |
| `red-team` | у EL с полномочиями нет THR |
| `draft-normative` | EL → статьи устава; или обратная проверка текста на соответствие |
| `lint-and-trace` | CI красный; перед PR |

Что агенты могут: всё в статусе proposed/draft/open/done. Что не могут: мержить, менять
аксиомы, переводить в accepted, тестировать своё.

**Об агентном моделировании.** Оно полезно для трёх вещей: найти дыры в процедуре (walkthrough),
заполнить карту разногласий (roleplay), сгенерировать атаки (red team). Оно бесполезно для
оценки исходов: агенты обучены на тех же текстах, что и `precedents/`, и воспроизводят
конвенциональную мудрость. Правило `CONSTITUTION.md` §4: находка симуляции становится
доказательством только после перевода в мысленный тест, проверяемый человеком без агента.
